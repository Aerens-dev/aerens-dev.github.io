Panel

Nothing built. Board not ordered.

A 280 × 456 touchscreen on the desk, running firmware largely written by an agent, showing the one thing about that agent worth knowing at a glance.

Two projects in one, and the survey says the second is the hard one. Putting a useful display on a microcontroller is a solved problem. Writing the firmware with an agent is not, and the reasons are specific enough to design around.

What is actually broken

The loop is the wrong length

An agent works by trying something and reading what happened. On the desktop that is seconds. On a microcontroller it is edit, compile, flash, boot — and the agent is idle through all four.

Which is why the interesting work in this space is not better code generation, it is removing the compile step. A sandboxed runtime that accepts new code over the network turns a firmware loop back into a software loop.

Nothing comes back

The compiler will tell an agent the code built. Nothing tells it the pin was misconfigured, the pull-up is missing, or the screen simply stayed dark. Compiler-in-the-loop and flash-in-the-loop both miss every error that only exists once the thing is running.

So the first thing to build is not firmware, it is the tool that reads the device back — flash, reset, stream the console, dump a variable. Bitcraze did this for the Crazyflie and reported the agent going from useless to autonomous on the strength of it.

An agent that can write code can be talked into writing bad code

If a device accepts code from a model, and a person can talk to the model, then a person can put code on the device. On a thing sitting on your home network that is a real problem, not a theoretical one.

The answer is not to review what the model wrote. It is to make the dangerous thing unreachable: expose the display and the buttons through a driver API and withhold the network stack and the firmware. The capability boundary is the security model.

Models are blind to deadlines

Interrupts, scheduling, priority inversion, races. This is the documented weak spot — code that reads correctly and misses a timing constraint that was never written down anywhere it could read.

Keep the agent above the clock. Generated code draws and reacts and is allowed to be late; the firmware underneath owns anything with a deadline. The split is not about trust, it is about which half has a testable failure.

A screen invites you to put too much on it

280 × 456 is enough pixels to be tempting and nowhere near enough to be a dashboard. The ambient-display literature has a blunt test for this: if it takes longer than about a second to understand, it is not peripheral, and putting it here makes a second screen to read.

Blocked or not blocked. Which session. What it is asking. Everything past that belongs on the monitor.

What a screen has that a light does not

This is the panel's reason to exist next to a keypad, and it comes out of the macropad research. Users approve around 93% of agent permission prompts and miss one dangerous request in three, because the requests all look the same.

A light can tell you something wants you. A screen can tell you it wants to run rm -rf, and that is the difference between a faster decision and a better one. Anthropic's Bluetooth API sends the tool name and the argument, which is precisely what a light cannot show.

Tools have to be shaped for a thing that cannot see

An interactive prompt is unusable to an agent — it fires a command and reads what comes back, and a live session with a cursor blinking in it is a dead end.

A daemon holds the connection; the agent sends one-shot commands against it. Same functionality, and the difference between a tool an agent can drive and one it cannot.

The board I own is the wrong one

The 1.64 AMOLED has a vendor repo created in August 2026 with no stars and no forks, and no audio codec — so it is a display, not an assistant, whatever the demos suggest. The 1.8 and the 2.06 have real ecosystems around them.

Not a reason to abandon it, but a cost to name out loud: on this board every problem gets solved alone. Decide that before ordering, not after.

Nobody will install a toolchain to try your project

A firmware project whose first step is "install ESP-IDF" has an audience of people who already have it, which is nearly nobody.

Flash it from the browser. Web Serial does this today, and a visitor with the board should be running it a minute after landing on this page, without a toolchain and without a download.

The device is not the deliverable

Which is the conclusion the other nine point at. A panel on a desk is a photograph. The interesting output is the tooling that made it possible to write firmware this way at all.

A skill that scaffolds and verifies, a CLI that closes the loop, a sandbox that makes generated code safe to run. Three things that are still worth having if the board ends up in a drawer, and one that is not.

Order of work

  1. Decide the board. The 1.64 is what is in the drawer; the 2.06 has people in it. This is the only decision that is expensive to reverse.
  2. Build the agent CLI first — flash, reset, console, variables — because nothing above it works until the loop is closed.
  3. Then the sandbox, or adopt one. Hot reload is what makes the rest pleasant rather than possible.
  4. Then one screen: blocked or not blocked, which session, what it is asking. Resist the second screen.
  5. Browser flashing on this page, and replace it with what happened.
