Superloop, state machine, RTOS

Three architectures, the one question that picks between them, and the two bills an RTOS sends.

Tutorial 05 of 07 · 30 minutes

Afterwards you can

  • Say why a superloop's worst-case latency is the sum of everything in it
  • Turn one long blocking job into a run-to-completion state machine
  • Name the two costs of an RTOS, and the deadline count that justifies them

The question

Your control loop ran at 1 kHz. You added logging to an SD card. The control loop now runs at 24 Hz, and nothing in the control loop’s code changed.

The instinct at this point is to reach for an RTOS, because that is what you do when a system has more than one thing to do. Sometimes that is right. Often it is buying a scheduler, a stack per task and a new category of bug in order to solve a problem that a hundred lines of state machine would have solved without any of them.

This tutorial is about which of three architectures a system actually needs, and the question that decides it is narrower than it looks.

Add one slow job, delay everything

In a plain superloop, each pass calls everything in turn. The worst case wait for any one task is therefore the total duration of every other task, and that is a property of the whole loop rather than of any task in it.

That is why the SD write destroyed the control rate. The write takes 40 ms because the card occasionally goes away to do internal housekeeping, and during that time the loop is inside a blocking call. The control code is unchanged, still correct, and now running at 24 Hz.

The property to notice is that nothing local tells you. Reviewing the control loop shows nothing wrong. Reviewing the logging code shows a normal blocking write. Only the composition is broken, and composition is what no file displays.

Cut the long job into short ones

The fix that does not need a scheduler is to stop having long jobs.

An event-driven state machine keeps the loop, but every function it calls must run to completion quickly and return. A long operation becomes a sequence of states: instead of one call that writes 8 kB and blocks for 40 ms, you get sixteen visits that each push 512 bytes into a peripheral and return in 40 µs.

The state is an ordinary enum, the transitions are a switch, and the whole thing is inspectable — you can print the current state, log the transitions, and assert that an event arriving in the wrong state is a bug rather than a surprise. Samek’s argument is that most embedded systems are state machines already, and the only question is whether the states are written down or scattered through flags.

This is the architecture most projects should reach for second, and most reach for never.

What an RTOS buys, and what it charges

An RTOS buys two real things. Independent deadlines — a high-priority task meets its deadline regardless of what a low-priority one is doing, because the scheduler preempts. And blocking calls that read naturally: read(); wait(); process(); in a straight line, instead of a state machine turned inside out.

The second is a bigger deal than it sounds. A protocol with eight sequential steps is unpleasant as a state machine and obvious as a task.

It charges twice. A stack per task, each sized by somebody’s guess, and eight tasks at 1 kB is 8 kB of RAM gone before any work is done — go back to tutorial 06 and see what that does to the budget. And a whole class of bug that a superloop cannot have: races, deadlock, priority inversion. In a superloop, two functions cannot interleave. Under a scheduler they can, at any instruction boundary, and only sometimes.

Priority inversion

The classic, and worth knowing by name because it is the one that will not reproduce.

A low priority task takes a lock. A high priority task tries to take the same lock and blocks — correct so far, and bounded by how long the low task holds it. Then a medium priority task, which wants nothing to do with the lock, becomes runnable and preempts the low one.

Now the medium task runs, the low task cannot run to release the lock, and the high task waits behind both. The highest-priority work in the system is effectively running at the medium priority, and there is no bound on how long that lasts. This is what put Mars Pathfinder into a reset loop on the surface in 1997.

The fix is priority inheritance: while a low-priority task holds a lock that a high-priority task wants, it temporarily runs at the high priority. FreeRTOS mutexes do this and its binary semaphores do not, which is the practical reason to use a mutex for mutual exclusion and keep semaphores for signalling.

The question that decides it

Not “how big is the system” and not “how important is it”. The question is how many genuinely independent deadlines are there.

One or none — a superloop, and no apology needed. Most motor controllers, most sensor nodes, most of what this course builds. It is the easiest thing to reason about and the easiest to measure.

A few, with some long jobs — event-driven state machines. The long job stops being long and the superloop keeps working.

Many, genuinely unrelated — an RTOS. A device doing motor control at 10 kHz, a TCP stack, a filesystem and a display has four unrelated deadlines and no sensible superloop.

The flight controller in track 8 is the interesting case: the rate loop at 8 kHz and everything else. That is one hard deadline and a pile of soft ones, which is why real flight controllers run the rate loop in an interrupt and the rest in a superloop underneath it.

Worked example: rescuing the 1 kHz loop three ways

The opening system: control at 1 kHz, and an 8 kB SD write that blocks for 40 ms once a second.

Option A — superloop with the write split by state machine.

The write becomes sixteen 512-byte pushes through DMA, one per pass, each costing 40 µs of CPU to set up.
Control loop budget 1,000 µs
Control work 180 µs
Log state step 40 µs
Worst case pass 220 µs
Control rate achieved 1 kHz, with 78% headroom

Logging now takes 16 ms of wall clock instead of 40 ms, spread across 16 passes. The control loop never notices. Cost: about 120 lines and one enum.

Option B — FreeRTOS, two tasks.

Control at priority 3, logging at priority 1, a queue between them.
Control task stack 1.0 kB
Log task stack, needs the FatFs buffers 2.5 kB
Idle task stack 0.5 kB
Kernel objects, queue of 32 samples 0.9 kB
RAM added 4.9 kB
Context switch, 84 MHz 3.4 µs, twice per switch
Control jitter ±8 µs from switch latency

It works, it reads better than option A, and it costs 4.9 kB of the 38 kB spare from tutorial 06’s budget. Also: the queue is now a place where a race can live, and the log task’s stack is a guess until measured.

Option C — rate loop in an interrupt, everything else in a superloop.

Control moves into the timer ISR at 1 kHz. Logging stays a plain blocking write in the main loop and is allowed to take its 40 ms.
Control jitter ±0.4 µs, interrupt latency only
RAM added 0
Log latency 40 ms, and nothing cares
Constraint control must fit in 180 µs and use no blocking call

Which one. C, for this system, and it is worth being clear why: there is one hard deadline, and an interrupt is a one-task scheduler that is already in the silicon and costs nothing. B becomes right when there are three or four such deadlines and the interrupt approach runs out of priorities to arrange. A is the right answer when the long job is one you control and the deadline count is still one.

The general shape: pay for a scheduler when you have more independent deadlines than the interrupt controller can express, and not before.

Do it

Twenty minutes, and step 1 is the measurement most projects have never made.

  1. Toggle a pin at the top of your main loop and measure the period on a scope, with the system doing its heaviest work. That is your real loop time, and the worst case is what matters rather than the average.
  2. Find the longest blocking call in your codebase and time it. If it is longer than your shortest deadline, you already have the opening problem.
  3. Take one long operation and rewrite it as a state machine with a switch and an enum. Measure the loop again.
  4. Then, if you run an RTOS: print the high-water mark for every task stack after an hour of load. The numbers are usually nothing like what was allocated, in both directions.
