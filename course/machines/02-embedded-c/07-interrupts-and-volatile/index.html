Interrupts, and why the variable needs volatile

What the hardware does before your handler runs, why the optimiser deletes your wait loop, and why volatile is not atomic.

Tutorial 02 of 07 · 30 minutes

Afterwards you can

  • Account for interrupt latency as a fixed overhead plus a variable critical section
  • Say what volatile promises, and name something it does not promise
  • Choose between disabling interrupts, an exclusive pair, and single-writer discipline

The question

Your firmware waits for a byte to arrive:

uint8_t ready = 0;
void USART2_IRQHandler(void) { ready = 1; }

while (!ready) { }        /* hangs for ever at -O2, works at -O0 */

At -O0 it works. At -O2 it hangs. Nothing about the interrupt changed; the handler still runs, and if you halt the debugger you can see ready is 1 in memory. The loop is spinning on a copy in a register that was loaded once, before the handler ever ran.

The compiler is not wrong. Nothing in the program it can see writes ready, so keeping it in a register is a legal and obvious optimisation. This tutorial is about the boundary between what the compiler can see and what actually happens.

From event to first instruction

Before your handler’s first line runs, the hardware does a fixed amount of work, and it is worth knowing the shape of it.

The core finishes or abandons the current instruction, then stacks eight registers automatically — this is why a Cortex-M handler can be an ordinary C function with no assembly wrapper. On an M4 that entry costs about twelve cycles, and the exit unstacking costs about the same.

The fixed part is small and predictable. The part that hurts is the first box: if a critical section is already running with interrupts disabled, the whole of it is added to the latency the peripheral sees. A 200 µs critical section somewhere unrelated is a 200 µs worst-case interrupt latency everywhere, and that is a global property of your firmware that no individual file shows.

What volatile promises

volatile tells the compiler: this object may change in ways you cannot see, so do not cache it in a register, do not remove accesses to it, and do not reorder those accesses with respect to each other.

That is exactly the promise the opening example needs, and exactly why the bug only appears with optimisation on. At -O0 the compiler reloads everything anyway, so the missing qualifier costs nothing and hides.

Three things need it: anything an ISR writes and the main loop reads, anything memory-mapped, and anything modified by DMA. All three are the same situation — an agent outside the compiler’s view is writing to memory.

Note what it does not buy, since this is where the second bug lives: it makes no promise about ordering relative to non-volatile accesses, and it makes no promise about indivisibility at all.

Volatile is not atomic

counter++ on a volatile int is three operations: load, add, store. An interrupt landing between the load and the store runs to completion, writes its own value, and then your store overwrites it. The interrupt’s update vanishes.

volatile guarantees the load and the store both really happen. It says nothing about the gap between them.

There are three ways out, and the right one depends on the situation.

  1. Disable interrupts across the sequence. Correct, blunt, and it adds the length of that sequence to global worst-case latency. Fine for three instructions; not fine around anything with a loop in it.
  2. Use an exclusive pair — LDREX/STREX, or the C11 atomics that compile to them. The store fails if anything touched the address in between, and you retry. No interrupts are disabled, so latency is untouched.
  3. Arrange for exactly one writer. Often the cheapest fix by far: if the ISR only ever writes and main only ever reads, there is no read-modify-write to interrupt. A single-producer ring buffer with one index written by each side needs no locking at all.

The third is worth reaching for first, because it removes the problem rather than managing it.

Lower number preempts higher

Cortex-M priorities are inverted relative to intuition: numerically lower is more urgent, and priority 0 is the most urgent configurable level.

More importantly, they preempt. A priority 1 interrupt arriving while a priority 3 handler is running does not wait — it interrupts the handler, runs to completion, and returns into it. So a slow low-priority handler delays main and delays nothing else.

This is what makes a priority scheme a design rather than a setting. Group your interrupts by deadline, not by importance: the motor current loop that must run every 50 µs goes high, the UART that has a 16-byte FIFO to absorb jitter goes low, and the button that a human presses goes lowest.

One trap on parts that implement fewer priority bits than the eight the register has: the bits are the most significant ones. Writing 1 and 2 into a four-bit implementation gives you 0x10 and 0x20, which works — but writing values that differ only in the low bits gives you two interrupts at the same effective priority, and no preemption between them.

What a handler may do

All the rules follow from one fact: the handler is spending somebody else’s stack and somebody else’s time. Whatever it does is charged to code that had no say in it.

No printf. Hundreds of bytes of stack and possibly milliseconds, both taken from whatever it interrupted. No blocking wait — the event you are waiting for may need this core, so the wait can never end. No malloc, because the allocator’s lock may already be held by the code you interrupted, which is a deadlock rather than a slowdown.

What is left is the pattern: read the hardware, put the data somewhere, set a flag, return. Do the work in the main loop where it can be interrupted in turn. A handler that runs in under a microsecond is invisible to the rest of the system, and that is the goal.

Worked example: a UART receive path that does not drop bytes

115,200 baud, 8N1. Ten bit-times per byte, so a byte arrives every 10 / 115200 = 86.8 µs, and if the part has no receive FIFO you must service each one within that window or the next overruns.

The wrong version, and why it survives testing.

void USART2_IRQHandler(void) {
    uint8_t c = USART2->DR;
    printf("got %c\n", c);          /* 2.4 ms at 115200 on the same UART */
}

That handler takes 2.4 ms. Twenty-seven bytes arrive while it runs and all of them are lost. It passes every test where you type one character at a time, and fails the moment anything sends a line.

The right version.

static volatile uint8_t buf[256];
static volatile uint8_t head;       /* written by the ISR only */
static volatile uint8_t tail;       /* written by main only    */

void USART2_IRQHandler(void) {
    buf[head] = USART2->DR;
    head = (head + 1) & 0xFF;       /* 8 bits, so the wrap is free */
}

Now count it. Four instructions, one peripheral read, one store, one masked increment: about 14 cycles, plus 24 cycles of entry and exit, so 38 cycles. At 84 MHz that is 0.45 µs, against a budget of 86.8 µs. The handler uses 0.5% of the available window.

Three details in there are load-bearing.

Each index has exactly one writer, so there is no read-modify-write to interrupt and no critical section anywhere in this code. That is fix 3 from above, and it is why this version needs no locking.

The buffer is 256 bytes and the indices are uint8_t, so wrapping is automatic and there is no comparison to get wrong. A 100-byte buffer would need a conditional, which is more instructions and one more thing to review.

The overrun case is still real. If main does not drain the buffer for 256 bytes — 22 ms — head laps tail and old data is silently overwritten. Silently is the wrong answer: add a dropped-byte counter in the ISR and expose it, because a system that loses data without saying so is worse than one that stops.

Do it

Twenty minutes. Step 2 is the one that makes it concrete.

  1. Take any ISR-to-main flag in code you have and remove volatile. Build at -O2 and confirm it hangs. Read the disassembly and find the load that was hoisted out of the loop.
  2. Toggle a GPIO pin high on entry to a handler and low on exit, and measure the handler on a scope. Compare it to what you guessed. Most people are out by more than 5×.
  3. Find the longest interrupts-disabled section in your codebase. That length is your worst-case interrupt latency, wherever it happens to live.
  4. Then the design question: take one shared variable between an ISR and main and see whether you can arrange single-writer discipline instead of a critical section. Usually you can, and the result is both faster and easier to reason about.
