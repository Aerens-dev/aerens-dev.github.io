Fixed point against float on a Cortex-M4

What the FPU actually does, the one character that costs thirty times, and when fixed point still earns its complexity.

Tutorial 06 of 07 · 30 minutes

  • Say what a bare decimal literal costs on a single-precision FPU
  • Choose a number format from the part, the data and the accumulator length

The question

Your control loop runs in 25 µs on the bench. You add one line to scale a setpoint — output = error * 0.5; — and it now takes 71 µs.

One multiply cost 46 microseconds. It did that because 0.5 is a double, and the part you are using has hardware for float and nothing at all for double, so the expression left the FPU and went into a software library.

The fix is one character. Knowing which character, and why, is most of what this tutorial is for.

Fixed point is integers with an agreement

Before floats, and still on parts without an FPU, arithmetic is done in fixed point: ordinary integers, with everybody agreeing where the binary point sits.

Q15 is the common one for signals. One sign bit, fifteen fraction bits, in a int16_t. So 0x4000 is 0.5, 0x7FFF is 0.99997, 0x8000 is −1.0, and the step size is 1/32768. The hardware sees plain integers throughout and has no idea a convention exists.

Addition and subtraction are free — Q15 plus Q15 is Q15, and it is just an integer add. Multiplication is where the convention shows: Q15 × Q15 = Q30, because you multiplied two fractions and got twice as many fraction bits. To get back to Q15 you shift right by 15.

int16_t a = 0x4000;                      /* 0.5  */
int16_t b = 0x2000;                      /* 0.25 */
int16_t c = (int16_t)(((int32_t)a * b) >> 15);   /* 0x1000 = 0.125 */

Two details in that line are the whole technique: cast to 32 bits before multiplying, or the product overflows; and shift by the number of fraction bits, not by 16. Forgetting the shift is the single commonest fixed-point bug, and it gives you an answer that is wrong by 32,768 rather than wrong by a little.

What the FPU actually covers

A Cortex-M4F has a single-precision floating point unit. float add, subtract and multiply are one cycle. Divide and square root are about fourteen, in hardware.

double is not in there at all. Every double operation goes to a software library and costs somewhere between 40 and 300 cycles.

And C’s default promotion rules mean you land in double without asking. A literal like 0.5 is a double. So x * 0.5 promotes x to double, does a software multiply, and converts back. Writing 0.5f keeps the whole expression in single precision and in hardware.

The same trap is in math.h: sin, cos, sqrt and atan2 all take and return double. The single-precision versions have an f suffix — sinf, cosf, sqrtf, atan2f — and on a hot path the difference is roughly 10×.

Two build settings are worth checking once and then forgetting: -mfpu=fpv4-sp-d16 -mfloat-abi=hard to use the unit at all, and -Wdouble-promotion to make the compiler point at every place you did this by accident. Turn the warning on before you go looking for the slow line by hand.

Error accumulates in the accumulator

Every format rounds. What matters is not the error in one operation, which is tiny in all of them, but how it behaves when you add up a million of them.

An integrator is the case that bites, because it is the one structure that deliberately remembers everything. A Q15 accumulator running at 1 kHz takes 3.6 million steps in an hour, and a half-LSB bias per step is a drift you can see on a plot. The same filter with a Q31 accumulator has 65,536× the resolution below the LSB and does not.

The rule that falls out: give the accumulator more bits than the signal. In CMSIS-DSP the FIR functions take Q15 input and Q15 output and use a Q63 accumulator internally, for exactly this reason. If you write your own, do the same — the intermediate type is where the precision has to live, not the interface.

For float, the equivalent care is not to add small numbers to a large running total. Once the accumulator reaches 10⁷, adding 1.0 to a float does nothing at all, because the step size at that magnitude is larger than what you added. Kahan summation fixes it, or a wider accumulator does.

Wrap or saturate

Integer overflow wraps. Add 1 to INT16_MAX and you get INT16_MIN — the largest positive value becomes the most negative one.

In a signal that is a click. In a control output it is full forward becoming full reverse, instantaneously, on a machine with mass. That is the difference between a glitch and a broken coupling.

So control code wants saturating arithmetic: at the top of the range it stops and stays there. That is also the physically correct behaviour, because the actuator has a limit and the maths should agree with it.

Cortex-M4 has this in the instruction set. QADD and QSUB saturate rather than wrap, SSAT clamps to any bit width you name, and both are single-cycle — so there is no performance argument for the wrapping version. In C they are reachable as __QADD and __SSAT through CMSIS.

This connects directly to anti-windup in track 4: an integrator that saturates at its output limit rather than wrapping is most of the way to not winding up.

What each situation wants

The short version is that float is the default now, and fixed point has to argue for itself. That was not true fifteen years ago and the folklore has not fully caught up.

A part with an FPU — M4F, M7, M33 — use float, put f on every literal, and spend the effort you saved somewhere useful. A part without one — M0, M0+, M3 — fixed point, because software float is 50 to 100× and that is not a rounding error. Data that is already integer — ADC counts in, PWM compare out — fixed point, since converting to float and back is work that buys nothing. A long-running integrator — either, but widen the accumulator.

The one thing not to do is what the folklore suggests: reach for fixed point reflexively on a part with an FPU, spend a week on Q formats, and produce something slower and much harder to read than float would have been.

Worked example: one biquad, three ways

A second-order IIR filter at 1 kHz on an 84 MHz Cortex-M4F. Five multiplies and four adds per sample. Measured with a pin toggle and a scope, not estimated.

Cycles per sample µs Loop at 1 kHz
double, literals unsuffixed 3,180 37.9 3.8%
float, every literal suffixed f 96 1.14 0.11%
Q15, 32-bit accumulator 71 0.85 0.085%

Read the gaps rather than the rows. Between double and float is 33×, and it costs one character per literal. Between float and Q15 is 1.35×, and it costs a rewrite, a Q-format convention to maintain, an overflow analysis, and a class of bug that does not exist in the float version.

So on this part the interesting decision is entirely the first one. The second is not worth making unless the loop is already at 80% and you have nowhere else to look.

Now change one thing: the same filter on a Cortex-M0+ at 48 MHz, which has no FPU.

Cycles per sample µs at 48 MHz
float, software library 1,240 25.8
Q15, 32-bit accumulator 84 1.75

15×, and now the rewrite pays for itself immediately. Same code, same filter, opposite conclusion — and the thing that flipped it was one line in the part’s feature list.

The transferable point: the format question has no general answer, and it has a very quick specific one. Look up whether the part has an FPU, then stop deliberating.

Do it

Twenty minutes, and step 1 usually finds something.

  1. Turn on -Wdouble-promotion and rebuild whatever you have. Count the warnings. Fix the ones on any path that runs more than a hundred times a second.
  2. Time a sin call and a sinf call with a pin toggle and a scope. The ratio is not what most people guess.
  3. Write the Q15 multiply from the section above, deliberately leave out the 32-bit cast, and watch the overflow. Then leave out the shift and watch the other failure.
  4. Then the useful habit: find one integrator in your code and check the width of its accumulator against the width of its input. If they are the same, it drifts, and you now know roughly how fast.
