The memory map, and where your bug lives

Four regions that behave nothing alike, what startup does before main, and why a stack overflow on a part with no MPU is a write rather than an error.

Tutorial 01 of 07 · 30 minutes

Afterwards you can

  • Name the region a given address falls in, and what a fault there implies
  • Say what the startup code does to .data and .bss, and what each costs
  • Explain why a stack overflow appears minutes after it happens

The question

A global counter is wrong. Not uninitialised, not off by one — it holds 0x0800A3F4, which is not a number your program ever computes. It is, if you look it up, an address in flash.

Nothing wrote that value on purpose. Something pushed a return address onto a stack that had run out of room, and the stack ran into your counter. On a desktop this is a segfault at the moment of the mistake. Here it is a write that succeeds, and the symptom arrives whenever somebody next reads that variable — which might be four minutes and a thousand function calls later.

Knowing the map is what turns that from a mystery into a lookup.

One map, four behaviours

A Cortex-M has one flat 32-bit address space, and it is carved into regions that have almost nothing in common except that they are addressable.

Flash at 0x08000000 holds code and constants. Reads are free; writes need an unlock sequence and erase a whole sector. SRAM at 0x20000000 holds everything that changes, and holds none of it across a reset. Peripherals at 0x40000000 are not memory at all — a read can clear a flag, and the region is gated off until you enable its clock. System space at 0xE0000000 is the core’s own: the interrupt controller, SysTick, the MPU.

The practical value is diagnostic. When a fault gives you an address, the top byte alone narrows the bug to one of four very different stories.

What runs before main

Your main is not the first code to execute. The reset handler runs first, and it does two things that explain a lot of otherwise confusing behaviour.

It copies .data from flash to RAM — every global with a non-zero initialiser exists twice, once as a template in flash and once as the live copy in RAM. And it zeroes .bss, which is why an uninitialised global is reliably zero while an uninitialised local is reliably garbage.

The cost model falls out of this directly. int table[1000] = {1, 2, ...} costs 4 kB of flash and 4 kB of RAM. static const int table[1000] costs 4 kB of flash and nothing in RAM, and on most parts is read directly from flash. On a device with 128 kB of RAM that difference decides whether the feature fits.

Two pointers, one room

RAM is shared between three things and only one of them is bounded at compile time. Static data sits at the bottom, fixed and known. The heap grows up from the top of static data. The stack grows down from the top of RAM.

Nothing arbitrates. The linker gives you a warning if static data alone exceeds RAM, and after that you are on your own: the stack’s depth depends on your call graph and your worst-case interrupt nesting, and the heap’s extent depends on your allocation pattern.

This is most of the reason embedded style avoids malloc. Not because allocation is slow, but because it makes the collision point depend on runtime history, and there is no allocator failure mode that a small device handles gracefully.

Overflow is a write, not an error

Here is the part that catches people arriving from a hosted platform.

On a system with an MMU, running off the end of the stack hits a guard page and raises a fault at the instruction that did it. On a Cortex-M with no MPU configured, there is no guard page and nothing to hit. The push simply succeeds — it writes to a perfectly valid RAM address that happens to belong to something else.

So the failure has three parts separated in time: the overflow, the corruption, and the eventual read of the corrupted thing. Only the third is visible, and it can be arbitrarily far from the first.

Two defences, and they are worth setting up before you need them. A guard pattern — fill the bottom of the stack with a known value at startup and check it periodically — costs a few lines and tells you the high-water mark. An MPU region marked no-access at the stack limit turns the overflow itself into a fault, at the instruction that caused it, which is the diagnosis you actually wanted.

Symptom, and where to look first

Enough of these recur that they are worth holding as a table rather than re-deriving each time.

A register that reads back zero is a gated peripheral until proven otherwise. Code that works until a particular call is stack depth. A hard fault at 0x00000000 is a call through a null function pointer — often an uninitialised callback. Something that is fine in debug and broken in release is a missing volatile or a timing assumption that only held because -O0 was slow.

And the worst one: a bug that changes when you add a print. Printing moves timing and consumes stack, so the diagnostic is also an intervention. When you see that, stop adding prints and reach for a pin toggle and a scope, which costs two cycles and no stack.

Worked example: does this firmware fit?

An STM32F411: 512 kB flash, 128 kB RAM. The application, counted honestly.

Flash RAM
.text — code 84 kB —
.rodata — const tables, strings 22 kB —
.data — initialised globals 6 kB 6 kB
.bss — uninitialised globals — 41 kB
Static total 112 kB 47 kB

47 kB of 128 kB used, so 81 kB free. That looks comfortable, and it is the point at which people stop counting. Two things are still missing.

The stack. Worst case is the deepest call chain plus the worst interrupt nesting on top of it. Measured with a guard pattern under load: 9.2 kB from the main path, and the DMA-complete handler at highest priority adds 1.4 kB on top of wherever it lands. Call it 11 kB, and note that this is a measurement rather than a calculation — a static analyser can bound it if you have no recursion and no indirect calls, and this firmware has both.

The DMA buffers. Two audio buffers of 8 kB each, double-buffered, so 32 kB, and they must live in a RAM region the DMA controller can reach — which on this part excludes the core-coupled memory that looked like free space.

RAM
Static 47 kB
Stack, measured worst case 11 kB
DMA buffers 32 kB
Total 90 kB
Free 38 kB

38 kB of headroom on 128 kB. Now read it back: the honest figure is 70% used, not 37% used, and the difference is entirely the two things that do not appear in the linker’s output. The number the map file gives you is the floor, not the total.

Do it

Fifteen minutes, and step 3 is the one worth keeping.

  1. Build any project you have and open the .map file. Find the four section totals. Most people have never looked.
  2. Add one initialised array of 1,000 integers and rebuild. Watch both flash and RAM move. Change it to static const and watch RAM come back.
  3. Fill your stack region with a known pattern at startup, run the firmware under its heaviest load for a while, then halt and find the deepest point the pattern was overwritten. That number is your real stack usage, and it is usually much larger than expected.
  4. Then, for the map: take the last hard fault you had and look up which region the faulting address was in. If you have never read the fault registers, this is the moment.

Check yourself

One question per idea on this page, 5 in all. Pick an answer and it tells you why. Nothing is scored and nothing is stored.

  1. 1What makes the peripheral region unlike the other three?

    Not quite. Peripheral access is slower than SRAM on most parts, and that is worth knowing. It is a performance difference rather than a behavioural one.

    Not quite. Backup domains aside, peripheral registers return to their reset values. Flash is the region that survives, and that is a separate distinction.

    Not quite. That describes flash. Peripheral registers need their clock enabled, which is different from an unlock and fails silently rather than refusing.

    Right. Many status registers clear a flag when read. It is not storage at all, so caching a read or reordering two of them changes behaviour.

  2. 2Why is an uninitialised global reliably zero while an uninitialised local is not?

    Not quite. That would cost one instruction per variable. It is done in bulk by the startup code, as one loop over a linker-provided region.

    Not quite. Erased flash reads as all ones rather than zeros, and mutable globals live in RAM. Only their initial values are stored in flash.

    Not quite. RAM contents after power-up are undefined and often not zero, and a warm reset leaves the previous contents. The zeroing is explicit.

    Right. The reset handler clears that whole region. A local lives on the stack, which nobody clears, so it holds whatever the last frame left there.

  3. 3What is the strongest argument against malloc on a small microcontroller?

    Not quite. Nearly all of them provide one, and it usually works. The objection is about what happens when it runs out rather than whether it exists.

    Not quite. Long uptime is a reason to worry more about fragmentation, not less. This argues against freeing rather than against allocating at all.

    Right. Fragmentation and allocation order decide when the heap meets the stack, so the failure is not reproducible and cannot be bounded at build time.

    Not quite. It is slower and less predictable than a static buffer, which matters inside an interrupt. It is a smaller problem than not being able to bound it.

  4. 4Why does a stack overflow on a part with no MPU appear far from its cause?

    Right. There is no guard page to hit, so the write is valid. Three events are separated in time and only the last, the read, is visible.

    Not quite. Small Cortex-M parts have no data cache to hold it, and where one exists it would not delay things by minutes. The delay is in the read.

    Not quite. Frames are set up on entry, so the space is claimed at the call. Deferring would not change that the write itself goes unnoticed.

    Not quite. No fault is raised at all, which is the whole difficulty. A fault that ran even late would still name the instruction responsible.

  5. 5A bug changes behaviour whenever you add a print. What does that suggest, and what should you do?

    Not quite. A race is one candidate among several, and locking before you know is guesswork. First get a measurement that does not disturb what it measures.

    Not quite. Clock changes do shift timing bugs around, which makes this a plausible experiment. It perturbs the system as much as the print did.

    Right. Printing costs time and stack, so the diagnostic is also an intervention. A pin toggle costs two cycles and no frame, and leaves the timing intact.

    Not quite. That can confirm an optimisation-sensitive bug, and it is worth trying. It also changes timing wholesale, so it moves the symptom for a second reason.
