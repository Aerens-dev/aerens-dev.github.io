Cascade: current inside velocity inside position

Three nested loops, why each one sees an easy plant, the limit at every handoff, and why the tuning order is forced rather than preferred.

Tutorial 05 of 06 · 30 minutes

Afterwards you can

  • Say what each loop in a cascade commands, and roughly how fast each should run
  • Explain why every loop in the stack needs anti-windup, not just the innermost
  • Tune a cascade from the inside out and say why the order cannot be reversed

The question

You want the shaft at 90°. The obvious approach is one loop: measure position, compute error, produce a voltage.

That loop has to cope with the winding’s inductance, the rotor’s inertia, friction that changes with temperature, back-EMF proportional to speed, and whatever the load is doing — all at once, with one set of three gains. It can be made to work and it is never very good, because a single set of gains cannot be right for dynamics that span four orders of magnitude in time.

The cascade is the standard answer and it is the structure every servo drive, every ESC and every flight controller uses. It is worth understanding as a decomposition rather than as a convention.

Three loops, each commanding the next

The stack, from the inside out:

Current loop, at the PWM rate — 20 kHz. Input: a torque request. Output: a voltage. This is the FOC loop from tutorial 17, and it converts current command into current against the winding’s electrical dynamics.

Velocity loop, ten to twenty times slower — 1 kHz. Input: a speed request. Output: a current command to the loop below. It sees the current loop as an ideal torque source, because from 1 kHz the 20 kHz loop looks instantaneous.

Position loop, ten times slower again — 100 Hz. Input: a position request. Output: a velocity command.

The rate ratio is the load-bearing part. Each loop must be fast enough that the loop above it sees it as a solved problem rather than as dynamics. Ten times is the usual minimum and twenty is comfortable, which is exactly the rule from tutorial 21 applied at each level.

Why this is easier

Compare what each arrangement has to model.

One loop confronts everything simultaneously: an electrical time constant of maybe 200 µs, a mechanical one of maybe 50 ms, friction, back-EMF coupling speed back into current, and load disturbance. One set of gains for all of it.

In a cascade, each loop sees roughly one integrator and a delay. The current loop sees an inductance. The velocity loop sees an inertia being driven by what is effectively an ideal torque source. The position loop sees an integrator. Each of those is a textbook plant that a PI controller handles well.

The second benefit is about disturbances, and it is the one that shows up on an oscilloscope. A disturbance is caught by the innermost loop that can see it, at that loop’s speed. A sudden load change alters current within microseconds and the 20 kHz loop corrects it before the velocity loop has taken a single sample. In a single-loop design, that same disturbance has to propagate all the way out to the position error before anything responds.

A limit at every handoff

Each loop’s output is the next loop’s setpoint, which makes every boundary a natural place for a limit — and each limit has a physical meaning, which is what makes the structure so pleasant to work with.

  • Position loop output, limited → maximum speed.
  • Velocity loop output, limited → maximum torque, which is your current limit and protects the motor and the bridge.
  • Current loop output, limited → maximum voltage, which is the duty cycle ceiling from tutorial 14’s bootstrap.

Setting a speed limit is now one line in one place, and it is enforced structurally rather than by hoping the trajectory generator behaves.

And here is the point most implementations miss: each of those limits can wind up the loop above it. If the velocity loop’s output is clamped at the current limit, the velocity loop’s integrator winds up exactly as tutorial 22 described. So every loop in the stack needs its own anti-windup, not just the innermost. This is the commonest omission in cascade code, and its symptom is a position loop that overshoots after any move long enough to hit the speed limit.

Tune from the inside out

The order is forced, not preferred, and the reason is simple: each outer loop’s plant includes the loop inside it. Tune the outer loop first and you are tuning against dynamics that are about to change.

  1. Current loop, with the shaft mechanically held. Removing motion removes back-EMF, so you are tuning against the winding alone, which is what you want.
  2. Velocity loop, with the current loop closed and its gains frozen.
  3. Position loop, with velocity closed and frozen.

Then the rule that follows from it: never go back and change an inner gain. If you do, every loop outside it is now tuned against a plant that no longer exists, and you must re-tune outward from the change. People discover this by adjusting the current loop to fix a noise problem and finding the position loop has started overshooting.

Worked example: adding position to the test stand

The stand has a current loop at 20 kHz (tutorial 17) and a velocity loop at 1 kHz (tutorial 19). Add position at 100 Hz.

Step 1 — check the rate ratios before tuning anything.

Rate Ratio to the loop inside
Current 20 kHz —
Velocity 1 kHz 20:1
Position 100 Hz 10:1

Both inside the 10-to-20 band. If position had been placed at 500 Hz the ratio to velocity would be 2:1, and the two loops would interact — which presents as an oscillation that changes when you retune either loop, and is one of the more confusing things to debug.

Step 2 — the position loop is P-only, and this is worth explaining. The plant it sees is velocity command in, position out, which is an integrator. An integrator already gives zero steady-state error to a step, so adding an integral term to the position loop gives you two integrators in series, 180° of phase lag, and no margin at all.

So: Kp only, and the tuning is one number.

Kp (RPM per degree) Rise Overshoot
4 480 ms none
12 190 ms none
30 95 ms 4%
60 70 ms ringing at 24 Hz

Take Kp = 12, a quarter of the ultimate, which is more conservative than the usual half because the position loop is the outermost and inherits every approximation below it.

Step 3 — set the limits and confirm each one does something.

Value Verified by
Position output limit 3,000 RPM commanding 180°, watching speed clip
Velocity output limit 10 A commanding a fast step, watching current clip
Current output limit 95% duty full-throttle command, scope on the gate

Step 4 — the bug this tutorial exists for. Command a 180° move. With anti-windup only on the velocity loop:
Time at the 3,000 RPM speed limit 310 ms
Overshoot past 180° 11°
Settle 1,400 ms

The position loop’s integrator— except it has none. So where is the overshoot coming from? From the velocity loop’s integrator, which is being held at a setpoint of 3,000 RPM by a position loop whose output is clamped. The velocity loop is not saturated and is tracking perfectly; the position loop is saturated and has no integrator to wind up.

The actual mechanism is simpler and worth stating plainly: the position loop is commanding maximum speed right up until the moment the error is small, so the load arrives at the target still travelling at 3,000 RPM and the deceleration is limited by the current limit. It is not windup at all — it is a trajectory problem, and the fix is not anti-windup.

Overshoot Settle
P-only position, speed clamp 11° 1,400 ms
Add velocity feedforward from a trapezoidal profile 0.4° 210 ms

Generating a trajectory that decelerates in time — a trapezoidal velocity profile — and feeding it forward removes the whole problem. The feedback loop is then correcting a small tracking error rather than discovering the stop.

That is the honest conclusion of this track: most of what looks like a tuning problem at the outermost loop is a trajectory problem, and the best control engineering available to you is often to ask for something the machine can actually do.

Do it

Twenty-five minutes, and step 4 is the one that ties the track together.

  1. Draw your own system as a cascade, even if it is currently one loop. Write down what each level would command and at what rate.
  2. Check the rate ratios. Anything under about 5:1 between adjacent loops is where interaction lives.
  3. Put a limit at every handoff and verify each one clips, by commanding something extreme and watching the intermediate signal on a scope.
  4. Then command a large step and watch whether the machine arrives at speed. If it does, generate a trapezoidal profile instead and feed the velocity forward. Compare the overshoot before and after — this is usually the largest single improvement available to a position loop.
