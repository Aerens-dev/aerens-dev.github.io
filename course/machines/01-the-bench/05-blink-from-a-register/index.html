Blink, from a register write

The four layers a HAL hides, the clock-gating bug everybody writes once, and why the field is cleared before it is set.

Tutorial 05 of 06 · 30 minutes

Afterwards you can

  • Enable a peripheral clock, and say what happens to register writes without it
  • Set one bit field without disturbing the other thirty bits in the register
  • Explain why a counted delay loop is not a unit of time

The question

You write the four lines that should blink an LED. You flash it. Nothing happens. You add a print, and the print appears, so the code is running. You read the register back and it is zero — the value you just wrote is not there.

Nothing is broken. You have left out one line that no compiler will ask you for, and it is the same line almost everybody leaves out the first time. This tutorial is about the layer where that line lives, and about why it is worth going down there at least once before going back up.

Four layers, and what each one hides

digitalWrite(13, HIGH) is four layers above a pin. Each layer is a decision somebody made for you, and each is fine until the moment something does not work, at which point all four become yours again with no documentation.

The Arduino-style call hides which port and which bit. The board package hides that the number on the silkscreen is not the number in the datasheet. The vendor HAL hides the clock enable, the mode, the output speed and the pull configuration — four separate registers. Underneath all of it is one store instruction to one address, and that instruction hides nothing at all.

The argument for going down here is not performance, although the difference is real. It is that the bottom layer is the only one whose behaviour is fully described by a document you can read.

The clock is off until you turn it on

Here is the missing line.

Every peripheral on a modern microcontroller comes out of reset with its clock gated off, because a peripheral with no clock burns almost no power and most applications use a handful of the dozens available. A GPIO port is a peripheral like any other.

With the clock off, writes to that peripheral’s registers are discarded. Not faulted — discarded. Reads return zero. There is no bus error, no exception, no warning, and the symptom is indistinguishable from having the wrong address.

RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;   /* the line everybody forgets */

On some families you must also let a cycle or two pass before the first access, because the enable takes effect on the peripheral bus rather than instantly. That one is in the errata rather than the reference manual, which is the previous tutorial’s point arriving early.

Two bits per pin

Now the mode register. MODER is one 32-bit word holding two bits for each of sixteen pins, and those two bits select input, output, alternate function or analogue.

So “make pin 5 an output” is not “set bit 5”. It is “write the value 01 into bits 11 and 10”, because pin n occupies bits 2n+1 and 2n. Getting this wrong by writing 1 << 5 configures pin 2 as an output and leaves pin 5 as an input, which produces a board that does nothing and a register dump that looks almost right.

The general habit: before writing any register, find its bit layout in the reference manual and work out the shift. Almost every peripheral register packs several fields, and almost none of them are one bit per thing.

Clear the field, then set it

Given a register with thirty other bits in it belonging to other pins, there are three ways to write your field and two of them are wrong.

Assignment — MODER = 1 << 10 — writes your field correctly and sets every other pin on the port to input. On a board where nothing else is configured yet this appears to work perfectly, which is what makes it dangerous: it fails later, when you add a second pin.

OR-assignment — MODER |= 1 << 10 — cannot clear a bit. It works from reset, where the field is 00, and silently fails to change anything if the field is already 10 or 11. This is the bug that survives testing, because it does the right thing exactly once, at startup, and the wrong thing on every reconfiguration.

Clear then set is the one that is always right:

GPIOA->MODER = (GPIOA->MODER & ~(3u << 10)) | (1u << 10);

Mask out the whole field with its width, then OR in the value. Verbose, and worth wrapping in a macro — but the macro should do this, not one of the other two.

A counted loop is not a unit of time

The last piece is the delay, and it is where the beginner’s blink quietly stops being a measurement of anything.

for (i = 0; i < 100000; i++); is a count of instructions, not a duration. The same source produces wildly different times depending on the clock source, the flash wait states at that clock, the optimisation level and whether the loop body touches anything the compiler considers observable. At -O2 with a non-volatile counter it is entirely legal for the compiler to delete the loop, and it will.

Use a timer peripheral, or SysTick, or at minimum a volatile counter you have measured. And measure the first blink on a scope rather than trusting it — the gap between the frequency you intended and the frequency you got is the most informative number in the whole exercise.

Worked example: the whole blink, in twelve lines

An STM32F4 with an LED on PA5. Everything, from reset to a pin that moves.

#include "stm32f4xx.h"

int main(void) {
    /* 1. Ungate the port. Without this the next three writes vanish. */
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;

    /* 2. PA5 to output: field 01 at bits 11:10, others untouched. */
    GPIOA->MODER = (GPIOA->MODER & ~(3u << 10)) | (1u << 10);

    /* 3. Push-pull, low speed, no pulls — all of these are already the
       reset values, and are written out because relying on a reset value
       you have not checked is how a working board stops working. */
    GPIOA->OTYPER  &= ~(1u << 5);
    GPIOA->OSPEEDR &= ~(3u << 10);
    GPIOA->PUPDR   &= ~(3u << 10);

    /* 4. SysTick at 1 ms, from the 16 MHz HSI this part starts on. */
    SysTick_Config(16000);

    while (1) { }
}

volatile uint32_t ticks = 0;

void SysTick_Handler(void) {
    if (++ticks % 500 == 0) {
        GPIOA->BSRR = (GPIOA->ODR & (1u << 5)) ? (1u << 21) : (1u << 5);
    }
}

Two things in there are worth stopping on.

BSRR rather than ODR. The bit set/reset register sets a pin by writing to the low half and clears it by writing to the high half — bit 5 sets PA5, bit 21 clears it. It is a single store with no read and no mask, so it is atomic against an interrupt that touches another pin on the same port. ODR ^= 1 << 5 is a read-modify-write, and if an interrupt changes PA3 in the middle of it, PA3’s change is lost. That is a real bug and it is very hard to find.

The measurement. SysTick_Config(16000) claims 1 ms from a 16 MHz clock, and 500 ticks claims 500 ms per edge, so 1 Hz. Put a scope on it. On a part where the HSI is specified as 16 MHz ±1% at 25 °C and ±5% over temperature, 1 Hz is actually 1 Hz ±5%, and you will read something like 0.98 Hz. That is not an error — it is the crystal you did not fit, and knowing that now is why the first blink is worth measuring rather than admiring.

Do it

Twenty minutes, and step 4 is the one that makes the point.

  1. Write the blink above for whatever part you have, from the reference manual rather than from an example. Expect it not to work the first time.
  2. Delete the RCC line and observe the failure mode: no fault, no message, the register reads back zero.
  3. Change the clear-then-set to |= and confirm it still works from reset. Then reconfigure the pin to analogue and back, and watch it stop working.
  4. Put a scope on the pin and measure the actual blink frequency to three digits. Work out where the difference from 1.000 Hz came from. That number is your part’s untrimmed internal oscillator, and it is why track 8 cares about a crystal.

One question per idea on this page, 5 in all. Pick an answer and it tells you why. Nothing is scored and nothing is stored.

  2. 2You write to a GPIO mode register and read back zero. What is the most likely cause?

    Right. A gated peripheral swallows writes and returns zero on reads, with no fault raised. It is indistinguishable from a wrong address until you check.

    Not quite. An MPU violation raises a memory fault rather than returning quietly. Silence with a zero read is the signature of a disabled clock.

    Not quite. A few registers do behave that way and the manual marks them. A mode register is plainly readable, which is what makes the zero informative.

    Not quite. Debuggers do sometimes show stale peripheral views, so it is worth ruling out. Reading in software gives the same zero, which points elsewhere.

  3. 3Why does writing 1 << 5 fail to make pin 5 an output?

    Right. The field is at 2n+1 and 2n. Writing bit 5 lands in pin 2's field instead, configuring the wrong pin and leaving pin 5 as an input.

    Not quite. It requires the two-bit value 01, which is why the shift matters. A single bit could not encode four modes.

    Not quite. Pin numbering starts at zero throughout. The offset comes from the field width being two bits, not from an off-by-one in the index.

    Not quite. Some peripherals do split sixteen pins across two registers, so the instinct is reasonable. The mode register packs all sixteen into one word.

  4. 4Why is OR-assignment the most dangerous of the three ways to write a bit field?

    Not quite. The code size difference is real and rarely matters. The problem is behavioural: a field already holding ones cannot be changed by ORing.

    Right. It cannot clear a bit, so it does the right thing once at startup and nothing thereafter. Testing a fresh boot never exposes it.

    Not quite. That is a genuine hazard and the reason BSRR exists, but plain assignment has no such window and is still wrong. The failure here is logical.

    Not quite. That is what plain assignment does. OR-assignment leaves the neighbours alone, which is why it looks so much safer than it is.

  5. 5At -O2 with a non-volatile counter, what does an empty counted delay loop compile to?

    Not quite. No such substitution happens — the compiler has no idea a delay was intended. It sees a counter nobody reads and removes it.

    Not quite. A write nobody reads is not observable, so the standard permits removing it. That is precisely what volatile exists to prevent.

    Right. The compiler may remove computation whose result is unused. Without volatile the counter is dead code and the delay disappears entirely.

    Not quite. Strength reduction can shorten loops that compute something. Here there is nothing to fold, so the whole construct is discarded.
